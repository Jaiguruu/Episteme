1. The three tiers & the call graph

One rule governs the whole layout: no language-specific shape may cross from Tier 2 to Tier 3. Tier 2 knows about grammars and throws its tree away. Tier 3 receives a fixed vocabulary of facts and never learns which grammar produced them.

The rule that shapes every module: grammar knowledge stops at ParseOutcome.

Who calls whom

Dependency direction is strictly one-way: offline/ → core/.

2. The data that flows

Five shapes carry everything. Each one is narrower than the last — bytes become a tree, a tree becomes facts, facts become identified entities.

3. core/ids.py

core maat/core/ids.py deterministic entity identity 150 lines · 8 functions · no state

Pure functions only. Every ID in the system is produced here, and every one is a truncated SHA-1 over a separator-joined tuple. There is no counter, no UUID, no id().

Every ID is prefix + sha1(parts joined by \x1f)[:16]. The preimage is the whole design.

The decision that makes incremental indexing possible model_version is not part of any ID. It is an attribute of the entity, not part of its identity. If version were in the preimage, an unchanged symbol would get a fresh ID on every reindex and the carry-forward in pipeline._reuse() would be impossible — which would make §9 AC2 (100 files → 0 reparsed) unachievable.
D27 — how this signature changed in M2 model_version_id(file_hashes_digest, pipeline_fingerprint=PIPELINE_FINGERPRINT) now takes a second input. Resolution changes the model without changing any file, so one content hash would otherwise map to two different models sharing one version ID. maat/core/ids.py carries two fingerprints — PIPELINE_FINGERPRINT (offline.stages=0-5;semantic=absent) and PIPELINE_FINGERPRINT_RESOLVED (offline.stages=0-5;semantic=stages6-8) — so a resolved model and an unresolved one built from the same bytes mint different versions, and reuse cannot serve an unresolved model as if it were the resolved one. Every version ID changes once, so an existing .maat/ index rebuilds on first use.

5. core/enums.py

core maat/core/enums.py closed vocabularies — the persisted contract 175 lines · 9 enums · 1 base class

No logic except two derived properties on ParseStatus. These values are written into ir.json, so adding a member is compatible and renaming one is not.

Declared but unused — do not delete without a decision ChangeKind, SymbolType.PARAMETER / VARIABLE / IMPORT, RelationshipType.REFERENCES / IMPLEMENTS are forward-looking schema. §11 of the spec asks the extractor for "References" and "Implementations"; M1 produces neither.

6. core/contracts.py

core maat/core/contracts.py the canonical semantic model 654 lines · 11 dataclasses

Mostly data, but the problems() methods are where the honesty rules are actually enforced. Validation never raises — every object returns a list of human-readable strings.

The one line that makes the whole honesty story testable if idgen.is_unresolved_target(self.target_symbol_id) and not self.target_name: issues.append("an unresolved relationship must record target_name")
Together with the two confidence rules, this means an edge can be unresolved or confident — but never confidently unresolved, and never unresolved with no record of what it was looking for.

7. core/serialization.py

core maat/core/serialization.py canonical JSON + atomic writes 112 lines · 5 functions

Where determinism is easiest to lose, and where §9 AC6 (interrupted update) is actually implemented.

FunctionBehaviour worth remembering
model_digest(ir)Calls ir.to_dict(), pops "counts", then SHA-256s the canonical JSON. The counts pop is why the determinism test passes even though created_at differs between runs — created_at lives inside ModelVersion, which is not part of ir.to_dict() at all.

8. offline/languages.py

tier 1 maat/offline/languages.py path → grammar key · extraction coverage 208 lines · 61 specs · 6 functions

One explicit table of 61 LanguageSpecs, two derived indexes built at import time, and a detection function. No grammar is written here — the grammars come from tree_sitter_language_pack.

Why not the pack's own detector detect_language_from_path maps .csv to a CSV grammar and .txt to a text grammar. Those are not source code and must not enter the semantic model as if they were. An explicit table is also reviewable and deterministic, which §8 AC5 requires.

display_name() and registry_summary() are reporting helpers; registry_summary() is currently untested (see TODO.md §6).

9. offline/snapshot.py

tier 1 maat/offline/snapshot.py Stage 1 — deterministic file manifest 341 lines · 9 constants · 8 functions

Walks the filesystem, classifies every file, hashes the survivors. Determinism comes from never trusting filesystem order.

Two independent determinism mechanisms: sorted walk, and a final sort by path.

The exclusion constants (159 entries total)

IGNORED_DIRECTORIES50Matched case-insensitively at any depth. Includes .maat — without it the index would be scanned on the next run and grow every time.

GENERATED_PATH_MARKERS6/gen/ is deliberately absent — it reads like "generated" but is a common ordinary package segment (com/example/gen), and using it silently dropped every Java file under such a package.
GENERATED_SUFFIXES13_pb2.py, .pb.go, .min.js, .freezed.dart…
GENERATED_CONTENT_MARKERS8@generated, DO NOT EDIT, Code generated by… searched in the first 8 KB.
The asymmetry that decides all three detectors A false positive silently removes real source from the model. A false negative merely leaves generated code in it. The model can be queried about generated code; it can never be queried about code that was never indexed. So every heuristic here is biased toward keeping files.
Why excluded files are recorded rather than dropped §8 AC4 says ignored/generated/binary files are excluded. Excluding them silently would be worse than including them — "why is my file missing?" deserves an answer. So they land in snapshot.excluded with a FileKind reason and are counted, but never reach the parser.

10. offline/changes.py

tier 1 maat/offline/changes.py Stage 2 — what needs reprocessing 153 lines · 4 functions

Three set differences plus one pairing algorithm. The interesting part is what it refuses to do.

A rename is scheduled for parse — and that is correct §9 AC5 asks that a rename "does not unnecessarily trigger semantic recomputation when content is unchanged and cache policy allows reuse". Our cache policy does not allow reuse: symbol_id is derived from the file path, so moving a file changes the identity of every symbol inside it. Reusing the old parse would leave the model keyed to a path that no longer exists. The recomputation is therefore necessary, not unnecessary — and the rename is still reported separately so callers can see what happened.

11. offline/parser.py

tier 2 maat/offline/parser.py Stage 3 — tree-sitter adapter 358 lines · 2 dataclasses · 8 functions

The module's own docstring states the point precisely: tree-sitter is error-tolerant by design and always returns a tree, so the work here is not recovery, it is classification. Nothing raises.

The status ladder is a strict order: EMPTY → UNSUPPORTED → OK → FAILED → PARTIAL.

13. extractors/query_extractor.py

tier 3 maat/offline/extractors/query_extractor.py one engine, 18 languages 538 lines · the largest module

The most complex file in M1. What makes it work across grammars that agree on almost nothing is three mechanisms, stated in its own docstring.

extract() — the phases, in order

What the binding phase deliberately does not do No deduplication. Rebinding is real — x = A(); x = B() genuinely binds x twice, and collapsing it would move a future resolver's "last write wins" decision into the extractor.
No resolution. type_name stays the raw text the source used.
But it does sort. facts.bindings.sort(key=lambda b: (b.span, str(b.scope), b.bound_name)) — so "last write in source order wins" is a property of the source, not of the order the query engine happened to match in.

14. offline/ir_builder.py

tier 3 maat/offline/ir_builder.py Stage 5 — facts become identified entities 483 lines · 9 functions

Where identity is created. Three things happen here that happen nowhere else — and each is a decision.

The prefix differs per family (module: / type: / call:) but the shape is identical — an honest placeholder.

Why target_name is passed to _relationship() as the ID key idgen.relationship_id(source_id, type, target_name or target_symbol_id, line, col)
The ID keys on the raw observed text, not the resolved target. That is what will let M2 resolve an edge without renumbering it — which is why M2 must never clear target_name. Clearing it would make every resolved edge look like a brand-new edge to the change detector.

15. offline/pipeline.py

orchestration maat/offline/pipeline.py owns the version and the reuse decision 579 lines · 3 dataclasses · 6 functions

Orchestrates all five stages and owns the two things no individual stage can: the model version, and what to reuse.

Why re-stamping carried entities is not a contradiction A symbol reused from V1 is re-emitted as belonging to V2. Its identity (the ID) deliberately excludes the version, so re-stamping does not change who it is. But §19 AC3 requires every published entity to reference the same active version. Carrying V1 entities into a V2 model unmodified would produce exactly the mixed-version state §19 AC1 forbids.
The subtle part of _reuse() It carries the previous parse outcome across, not just the entities. The fresh snapshot can only guess a provisional status for a source file — it does not parse anything. Without this, an unchanged file that was PARTIAL or FAILED would silently be reported as OK on the next run, and the degradation would vanish from maat status while the broken code was still there.
Fixed — load_previous_ir was not defensive Its docstring promises "a corrupt file is treated as absent, matching the manifest policy", and that promise was once false. The guard wrapped json.load, but the rehydration that followed sat outside the try. Probed: a missing field raised KeyError, an unknown enum value ValueError, a wrong collection type TypeError — all of which propagated out of index(). The guard now wraps rehydration too, catching narrowly (AttributeError, KeyError, TypeError, ValueError) and reporting absence, so a drifted model triggers a rebuild instead of aborting the run. {} is structurally valid, so it still loads — and is measured harmless: it yields nothing reusable, so unchanged files fall through to the parse branch. Contrast load_manifest in changes.py, which was already defensive at every level.

Where resolution plugs in

The resolution phase sits between _sort_ir(ir) and ir.problems() — after the model is assembled and ordered, before validation gates publication. That placement matters: validating a resolved model is what §14 asks for, and publishing only a validated one is what §19 AC2 asks for. It is opt-in (resolve=True), so the default path is unchanged.

16. queries/*.scm

tier 2 maat/offline/queries/ declarative extraction — the extension point 18 files · 0 lines of Python

Adding a language means adding data, not code. The presence of a .scm file is the definition of extractability.

Query files are compiled once per language (lru_cache(128)) and cached as ts.Query objects. A compile failure becomes a QueryUnavailableError, which the extractor converts into an extract.no_query diagnostic rather than an exception.

The most expensive M1 lesson, and it is still the top M2 risk Never guess a grammar node name. A wrong node name fails silently — the pattern simply matches nothing and yields zero captures, which looks identical to "this language has no such construct". Every new pattern must be written against tools/probe_bindings.py output for the actual grammar.

17. End-to-end trace — one call edge, all five stages

Following self.repository.save(payment) in services/payment_service.py from bytes to an unresolved edge — the trace M1 emits by default, and the edge Stage 6 resolves when resolve=True.

Where Stage 6 intervenes, in one sentence Between ⑤ and ⑥, or just after _sort_ir(ir): the BindingFact produced in ④ persists as a Binding collection and is re-stamped on reuse, and Stage 6's resolve_ir() reads it when resolve=True — upgrading the ⑤ UNRESOLVED edge above to a real target. With resolve=False (the default) every reference still leaves ⑤ UNRESOLVED.
